# Migration 0.2.0 — the skill library, and the rewritten protocol

**Takes a vault from 0.1.0 to 0.2.0.** Large: budget an hour, with the owner present.

Read [../UPDATES.md](../UPDATES.md) first. It resolves the vault, recovers this owner's placeholder values,
and holds the safety contract. This document assumes all of that already happened.

---

## Read this before you start

**This is not a patch. It is a guided re-seed of the vault's protocol and skill files, with the owner in the
loop.**

0.1.0 to 0.2.0 rewrote most of the kit: about 3,600 lines changed across 38 files. Every protocol document
in the vault was substantially reworded. There is no honest set of small anchored edits that gets from one
to the other, and pretending otherwise would have you paste large blocks into a file whose surrounding text
no longer matches.

So the method here is different from every other migration in this folder. **You replace the vault's
protocol and skill files wholesale, after showing the owner each diff, and you never touch their
knowledge.** Their wiki, notes, sources, and deliverables are not involved at any point.

**The knowledge is safe either way.** Every `wiki/` page, every note in `inbox/` and `raw/`, and everything
in `outputs/` is untouched by this migration. What changes is the protocol the AI follows and the skill
files that carry it.

**A 0.1.0 vault keeps working.** The owner can decline this and lose nothing they already have. They would
only be declining the skill library and the rewritten rules. Say that plainly before you begin.

---

## What it adds

- **The skill library.** A folder beside the vault holding the one master copy of each built skill, with a
  registry, a per-machine install runbook, and a packaging script. The brain holds knowledge; the library
  holds methods.
- **`/brain-skill`** and the `skill-library` skill, with the two-gate offer rule: the owner will run the
  method again, **and** it is a business process, a personalization, or a way of working with AI they
  repeat. Minor process detail does not qualify.
- **A controlled tag vocabulary** in `wiki/_tags.md`, with retired-tag redirects, and a lint check for
  off-vocabulary tags.
- **The self-sufficient-note rule** in `SCHEMA.md` §6a. A note is filed from its own content, so a pointer
  the nightly run cannot reach never strands a note in the inbox.
- **A per-machine install runbook** at `<vault>/.claude/INSTALL.md`, with a drift check.

## Preconditions

| Must be present | If it is missing |
|---|---|
| `<vault>/SCHEMA.md` and `<vault>/wiki/` | Not a kit-built vault. Stop and ask the owner. |
| `<vault>/.claude/skills/capture-to-inbox/SKILL.md` | The skills were never installed from the vault, or they were renamed. Stop, list what is there, and ask. |
| A writable sibling location for the library | Ask for the path. The default is a sibling of the vault named `AI-Skills`. |

**Already has `.claude/skills/skill-library/`?** Then the vault is at 0.2.0 or partway there. Do not re-run
this. List what exists, compare it to the kit, and apply only the missing parts, each with the owner's yes.

## 1. Decide, with the owner, before writing anything

Ask these and wait. Each answer changes what you write.

1. **Has the owner edited `SCHEMA.md`, `PROCESS.md`, `CLAUDE.md`, `wiki/_conventions.md`, or any skill file
   since install?** If yes, ask what they changed and why. Those changes must survive. Carry each one into
   the new file by hand, after the replacement, and show them the result.
2. **Where does the library go?** A sibling of the vault, in the same synced storage. Confirm the absolute
   path and the folder name.
3. **What is their identity list?** Read it from `SCHEMA.md` §5. Confirm it back to them. 0.2.0 uses the
   same field, so it should carry over unchanged.
4. **Do they want the library at all?** It is the bulk of this version. A vault can take the rewritten
   protocol and skip the library. If they skip it, omit sections 3 and 5 below, and say so in the record.

---

## 2. Replace the vault's protocol and skill files

**Back up every one of these first**, beside itself as `<file>.pre-0.2.0`.

Then copy each from `<kit>/seed-vault/` to the same relative path in the vault, and replace every
`{{PLACEHOLDER}}` with the value recovered in UPDATES.md Step 3.

```
SCHEMA.md            CLAUDE.md            PROCESS.md           README.md
wiki/_conventions.md wiki/_tags.md
.claude/INSTALL.md
.claude/skills/capture-to-inbox/SKILL.md
.claude/skills/process-inbox/SKILL.md
.claude/skills/maintenance-pass/SKILL.md
.claude/skills/skill-library/SKILL.md
.claude/commands/capture.md  process.md  pull.md  maintain.md  brain-skill.md
```

**Show the owner a diff for each file before you write it.** Not a summary of the diff — the actual
changes. These are the rules their brain runs on, and they are entitled to see what changed.

**Do NOT replace `wiki/_index.md` or `wiki/_log.md`.** Those are theirs. The index catalogs their pages and
the log is their append-only journal. The seed's copies are empty scaffolds and would erase both.

**Then carry their edits back in**, one at a time, from the answers in section 1 and from the `.pre-0.2.0`
backups. Show each one. Where their change and the new wording genuinely conflict, put the choice to them
rather than picking.

### `wiki/_tags.md` needs real work

0.2.0 makes tags a **controlled vocabulary**: only values listed in `wiki/_tags.md` are valid, and a retired
tag carries a redirect to its replacement.

The seed's `wiki/_tags.md` is a starter list. The owner's existing pages already use tags. So:

1. Grep every `tags:` line in `wiki/` and build the list of tags actually in use.
2. Show the owner that list beside the seed's starter list.
3. **Build their vocabulary from what they already use**, adding seed entries only where they want them.
   Never drop a tag that is live on a page — that turns every page using it into a lint finding.
4. Write the merged list. Record any tag they chose to retire, with its replacement, in the retired section.

**This is the step that goes wrong if you rush it.** A vocabulary that does not match the pages makes the
first `/maintain` pass after this update report dozens of false findings.

---

## 3. Create the library

Copy the contents of `<kit>/seed-library/` to the library path from section 1, and replace every
placeholder.

```
<library>/
  README.md  CONVENTIONS.md  INSTALL.md  registry.md
  skills/.keep
  tools/package-skill.py
```

`skills/` starts empty. It fills as the owner builds skills.

**Never leave a `.git` folder in the library either.** It is synced storage, the same as the vault.

**If the owner already keeps skills somewhere**, do not move them. Point the library at what exists: set
`SKILLS_DIR` to that folder, add the four library documents into it, and write a row in `registry.md` for
each skill already there. Moving someone's working skills is not this migration's job.

---

## 4. Reinstall the Claude Code copies

Follow `<vault>/.claude/INSTALL.md`, which this migration just created.

Set **`SKILLS_DIR`** in `~/.claude/settings.json` under `env`, beside the existing `BRAIN_DIR`, if the
library is not a sibling named `AI-Skills`.

**Every other machine needs the copy-install re-run.** Name them as a to-do.

---

## 5. Refresh the other surfaces

0.2.0 rewrote the instruction blocks for Cowork, claude.ai chat, and ChatGPT, and the ChatGPT builder prompt
gained the library.

These are **copies**, so they do not update through sync. For each surface the owner uses, hand them the
current block from `<kit>/docs/surfaces.md`, or the builder prompt from `<kit>/docs/chatgpt.md`, with their
paths filled in. **They paste it. You do not sign in to their accounts, and you do not create a custom GPT
for them.**

List any surface they decide to leave stale, so they know it is stale.

---

## 6. Verify

| Check | Pass looks like |
|---|---|
| `grep -r "{{" <vault>` and `grep -r "{{" <library>` | Both return nothing |
| New session offers five commands | `/capture` `/process` `/pull` `/maintain` `/brain-skill` |
| `/capture test note` from **outside** the vault | Writes into `<vault>/inbox/`, echoes the full path |
| `/pull` on something the wiki already covers | Cites real pages that existed before this update |
| `/maintain` | Runs clean, or reports findings the owner recognizes as real. A flood of tag findings means section 2's vocabulary merge was rushed — go back and fix it. |
| `wiki/_index.md` and `wiki/_log.md` | Still hold the owner's content, unchanged except the new log line |

---

## What this migration must not touch

`wiki/` page content. `wiki/_index.md`. `wiki/_log.md`, except the one appended `maintenance` line.
`inbox/`. `raw/`. `outputs/`. Any skill the owner built themselves.

**Never run git in the vault or in the library.**

---

## Rollback

Restore every `.pre-0.2.0` backup over its file. Delete the files 0.2.0 added:
`.claude/skills/skill-library/`, `.claude/commands/brain-skill.md`, `.claude/INSTALL.md`, and the library
folder if it was created new and holds no built skills.

Re-run the copy-install so `~/.claude/` matches the vault again, and delete
`~/.claude/skills/skill-library/` and `~/.claude/commands/brain-skill.md` by hand — the install copies files
in, and it never deletes.

Then append a `maintenance` line to `wiki/_log.md` saying the update was rolled back, and why.
